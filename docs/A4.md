## 1. 결과 요약

## 2. 상세 — A 담당 항목 화이트박스 대조 (A1~A3 경과 포함)

### 전제: A1(진단 환경) · A2·A3(블랙박스) 경과

- **A1 진단 환경**: 격리 랩(로컬 `127.0.0.1:8000` 바인딩, 더미 데이터)에서 요청 변조 기반 수동 진단 환경을 구성했다. 프록시/Repeater 역할의 요청·응답 캡처는 `curl`로 재현·보존했다(스크립트: Kali `~/a05/`). 블랙박스 단계에서는 소스를 열지 않았다.
- **A2(블랙박스 A01·A05)**: SQLi(공지 검색), 저장형 XSS(게시글·댓글), 게시글 IDOR, `/my/?child=` IDOR, SSRF 5건 재현 — `docs/A2.md`.
- **A3(블랙박스 A06·A07·A08)**: 전화 인증 OTP 약점, 로그인 무제한·세션 고정, 미검증 업로드, role 쿠키 변조 재현 — `docs/A3.md`.

아래 표가 3단계의 핵심이다: 블랙박스로 "밖에서 관찰한 현상"을 **소스의 원인 코드**와 묶었다.

### A 담당 취약점 ↔ 원인 코드 대조표

| OWASP | 취약점 | 원인 위치 (파일 · 함수) | 근본 원인 |
| --- | --- | --- | --- |
| A05 | SQL 인젝션 | `center/views.py` · `notice_list()` | `Notice.objects.raw(f"... LIKE '%{q}%' ...")` — 검색어를 문자열로 직접 결합 |
| A05 | 저장형 XSS | `center/views.py` · `post_detail()` | `mark_safe(post.body)`·`mark_safe(c.body)` — 자동 이스케이프 무력화 |
| A01 | 게시글 IDOR(수정·삭제) | `center/views.py` · `post_edit()`·`post_delete()` | `@login_required`만 있고 **작성자 일치 검사 없음** |
| A01 | 남의 아이 출결 IDOR | `center/views.py` · `my()`·`my_child()` | `?child=` 지정 시 보호자 필터를 건너뛰고 `pk`만으로 조회 |
| A01 | SSRF | `center/views.py` · `embed()` | `urllib.request.urlopen(url)` — 스킴·호스트 제한 없음(`file://`·내부망·메타데이터) |
| A01·A08 | role 쿠키 권한상승 | `center/views.py` · `board()` | `request.COOKIES.get('role') == 'staff'` 를 권한 근거로 사용 |
| A06(대체) | 가입 OTP 약점 | `center/views.py` · `signup_phone()` | 3자리 난수(`random.randint(100,999)`) + **응답에 노출** + 시도 제한 없음 |
| A07 | 세션 고정 | `center/middleware.py` · `SessionFixationMiddleware` | `?sessionid=` 수용 + `cycle_key` 무력화로 로그인 후 키 미재발급 |
| A07 | 로그인 시도 무제한 | `center/views.py` · `limited_login()` | 한도 상수·`_count_failure`/`_blocked`가 **정의만 되고 호출되지 않음**(죽은 코드) |
| A08 | 미검증 파일 업로드 | `center/views.py` · `my()` + `models.Upload` | `Upload(file=...)` 저장 시 형식·크기 검사 없음(`upload_to='docs/'`) |

> 참고: 같은 코드베이스에 **안전한 업로드 경로**(`models.NoticeFile` → 매직바이트 검증 + 저장명 재생성 + `notice_file()`의 `Content-Security-Policy: sandbox`)도 있다. 취약한 쪽은 `Upload`뿐이다. 화이트박스가 아니면 두 경로의 차이를 구분하기 어렵다.

### 누락 취약점 (블랙박스 미보고 — 신규)

1. **가입 시 `is_staff=1` 자기 승격 (A01/A07, High)** — `signup()`은 폼의 `is_staff` 값을 그대로 받아 `user.is_staff = True`로 저장한다. 공개 회원가입만으로 **직원 권한 계정**을 만들 수 있다. 블랙박스 A2·A3에 없던 항목으로, `W8 대조` 과정에서 발견했다. (라이브 확인: 3절)
2. **로그인 한도 코드의 무력화 (A07, 설계 결함)** — `limited_login()` 래퍼는 IP·아이디 해시를 계산하고 주석까지 달려 있으나, 실제로 `_count_failure()`·`_blocked()`를 **한 번도 호출하지 않는다.** "한도가 있어 보이는데 없는" 상태라, 코드 리뷰로만 드러난다.

| OWASP | PLAN 담당표 | 실제 소스 | 판단 |
| --- | --- | --- | --- |
| A06 | 추측 가능한 **비밀번호 재설정 토큰** | 재설정 기능 **없음**. 대신 `signup_phone()` 3자리 OTP·노출·무제한 | 성격은 동일(인증 설계 약점), 구현은 다름. `docs/C3.md`와 일치 |

## 3. 검증 — B 담당 항목 PoC 교차 재현

A4의 필수 요건(**B 담당 항목 PoC 1회 이상 교차 재현**)을 위해 로컬 실행본(Django 6.1.3, `seed_dummy`)에 대해 B2·B3 소견을 직접 재현했다. 전부 로컬·더미 데이터 기준이다.

### A10 — DEBUG 상세 오류 노출 (B2, High)
```
GET /notices/abc/          → HTTP 404, Django 디버그 페이지("DEBUG = True", "Using the URLconf")
```
원인: `config/settings.py` `DEBUG = os.environ.get('DJANGO_DEBUG','1') == '1'`(기본 ON). **B2와 일치.**

### A02 — 기본 관리자 계정 + 버전 노출 (B2, High / Low)
```
POST /login/  username=admin&password=admin1234  → HTTP 302 Location:/my/ + sessionid 발급
GET  /         → Server: WSGIServer/0.2 CPython/3.14.x  (CSP 헤더 없음)
```
원인: `seed_dummy`의 `create_superuser('admin', ..., 'admin1234')`, 서버 버전 헤더 노출. **B2와 일치.**

### A04 — 비밀번호 MD5 저장 (B2가 블랙박스로 못 본 것 → 화이트박스 확정, High)
```
settings.PASSWORD_HASHERS = ['django.contrib.auth.hashers.MD5PasswordHasher']
admin 저장 해시: md5$<salt>$<32hex>
```
B2는 "저장 방식은 블랙박스로 확인 불가, B4/화이트박스에서 확인"이라고 남겼다. **A4에서 소스·셸로 MD5 저장을 확정**한다(A2의 SQLi로 유출된 해시가 MD5였던 것과도 일치). 더불어 `SECURE_SSL_REDIRECT`·`SESSION_COOKIE_SECURE`는 `if not DEBUG`에서만 켜져, 개발·HTTP 구간에서 평문 전송된다(B2 A04와 일치).

### A09 — 로그인 실패 미기록 (B3, Medium)
```
틀린 비밀번호 로그인 3회 → security.log 변화 없음(login_fail 라인 0건)
올바른 로그인 1회        → security.log 에 login_ok 1건
```
원인: `limited_login()`이 성공(비-200)에만 `security_log.info('login_ok ...')`를 남기고 **실패(200 재표시)는 기록하지 않는다.** `export()`(CSV)도 로깅 호출이 없다. **B3와 일치.**

### A03 — 공급망 (B3, 취약점 없음)
`requirements.txt` 3종 모두 최신. 화이트박스로도 구버전·CVE 라이브러리 없음 확인. **B3의 "취약점 없음"과 일치**(미삽입 항목).

> **A 항목 라이브 재확인(참고)**: SQLi(`?q=' OR 1=1--`→공지 전건), role 쿠키 우회(비직원 세션+`role=staff`→`/attendance/board/` 200), `/my/?child=1`로 남의 아이(`모의아동01`) 조회, `signup` `is_staff=1`→직원 계정 생성, `signup_phone` 응답의 3자리 인증번호 노출을 모두 로컬에서 재현했다.

## 4. 남은 것·참고

- **W8 원본 재대조(최종 확정 대기)**: W의 비공개 W8 목록이 공개되면, 본 문서의 발견 목록과 1:1로 대조해 (a) 누락(blind spot), (b) 계획엔 있으나 미구현, (c) 계획에 없이 추가된 항목을 확정한다. 현재까지의 대조 기준은 `PLAN.md` 담당표 + `C3.md` + 소스다.
- **B 트랙으로 전달(교차 산출물)**: `signup()` `is_staff=1` 자기 승격은 A02(보안 설정)·A07(인증) 양쪽 성격이 있어 B4와 공유 권장. A03·A06 미삽입 건은 C3의 "범위 조정 필요" 논의와 연결된다.
- **4단계(조치·재검증) 입력**: A 발견 이슈의 `secure` 브랜치 조치 포인트는 — SQLi: 파라미터 바인딩/ORM, XSS: `mark_safe` 제거·CSP, IDOR: 소유자 검증(403), SSRF: 스킴·사설·루프백 차단, role 쿠키: 서버 세션으로만 권한 판정, OTP: 긴 난수·미노출·만료·시도 제한, 세션 고정: 로그인 시 `cycle_key`, 업로드: `NoticeFile`와 동일한 매직바이트 검증, `is_staff`: 가입 폼에서 권한 필드 제거, 로그인 한도: `limited_login`에서 실제 카운트 호출, A04: PBKDF2/argon2 해시·HTTPS·`Secure` 쿠키, A02: `DEBUG=False`·기본계정 제거·버전 숨김. → A5에서 재검증.
- **재현 환경**: 로컬 venv(Django 6.1.3)로 `migrate`→`seed_dummy`→`runserver` 후 `curl` PoC. 저장소 밖(scratchpad)에서 실행해 작업 트리를 더럽히지 않았다. 원본 PoC 스크립트는 Kali `~/a05/`.
