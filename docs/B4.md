## 2. 상세 — 담당 항목 근본 원인

### A10 — DEBUG 기본 ON

`config/settings.py:32`
```python
DEBUG = os.environ.get('DJANGO_DEBUG', '1') == '1'
```
- 환경변수 기본값이 `'1'`(켜짐)이고, compose도 `DJANGO_DEBUG=1`로 띄움. 오류 시 디버그 페이지(설정·코드) 노출.
- B2에서 `GET /notices/abc/` 404로 확인한 것과 일치. 운영 전환 시 `DJANGO_DEBUG=0` 필요(그때 `SECRET_KEY` 환경변수 강제 — `settings.py:40`).

### A02 — 약한 기본 관리자 계정

`center/management/commands/seed_dummy.py:53-54`
```python
User.objects.filter(username='admin').exists() or \
    User.objects.create_superuser('admin', 'admin@example.com', 'admin1234')
```
- 자격증명이 코드에 하드코딩. B2에서 흔한 조합 점검으로 로그인된 계정(`admin`/`admin1234`)과 동일.

### A04 — MD5 해시 + 조건부 쿠키 보호

`config/settings.py:27`
```python
PASSWORD_HASHERS = ['django.contrib.auth.hashers.MD5PasswordHasher']
```
- 비밀번호를 MD5(솔트 포함)로 저장. B2에서 "저장 방식은 B4에서 확인"으로 미뤘던 항목을 확정. 오프라인 크랙에 취약(S1이 SQLi로 유출해 `admin1234` 복원 — 3절).

`config/settings.py:184-187`
```python
if not DEBUG:
    SECURE_SSL_REDIRECT = True
    SESSION_COOKIE_SECURE = True     # 세션 쿠키를 https 로만 전송
    CSRF_COOKIE_SECURE = True
```
- 쿠키 `Secure`·SSL 리다이렉트가 `if not DEBUG` 블록 안에만 있음. DEBUG=1인 현재는 적용되지 않아 B2의 "쿠키 Secure 없음·HTTP 평문"과 일치.

### A09 — 로그인 실패 미기록 + 잠금 미작동

`center/views.py:122-126` (`limited_login` 래퍼)
```python
response = login_view(request)
if request.method == 'POST':
    if response.status_code == 200:      # 실패하면 폼이 다시 그려져 200
        pass
    else:
        security_log.info('login_ok ip=%s user_id=%s', ip, getattr(request.user, 'pk', None))
```
- 실패 분기(`status_code == 200`)가 `pass` — **기록도 카운트도 없음.** 성공만 `login_ok`로 남김.
- 잠금 함수 `_blocked()`(`views.py:100`)·`_count_failure()`(`views.py:104`)가 **정의만 되고 `wrapped`에서 호출되지 않음.** 함수 docstring의 "틀린 시도가 쌓이면 막는다"는 구현과 다름.
- B3에서 관찰한 "실패 미기록"의 코드상 원인. 동시에 **S1 A07(로그인 무제한 시도)**의 근본 원인이기도 함 → 교차 일치.
- CSV 열람(`/attendance/export/`)은 `export` 뷰에 `security_log` 호출 없음. `my` 뷰만 `views.py:353`에서 기록.

## 3. 교차 재현 — S1 A05 (SQL 인젝션)

- 대상: `/notices/?q=` 공지 검색 (S1 보고서 A2-1)
- 방법: UNION 주입으로 `auth_user`의 해시 유출
  ```
  GET /notices/?q=' UNION SELECT id,username||' = '||password,3,4,5 FROM auth_user--
  ```
- 결과(실측):
  ```
  admin = md5$<솔트>$<해시>
  ```
  (실제 해시 값은 세션/자격증명 노출 방지를 위해 보고서에 전체를 남기지 않음. `md5$` 접두어만 인용)
- 정상 검색(`q=독감`)은 공지만 반환 → 주입과 응답 차이로 취약 확인.
- **교차검증 의미:** S1의 A05 결과가 재현되고, 유출된 해시의 `md5$` 접두어가 제 A04(MD5 저장) 화이트박스 소견과 일치. 두 항목이 서로를 입증(SQLi로 뽑은 해시 = MD5 저장의 실제 피해).

## 4. 남은 것·참고

- **W8 대조는 최종 단계로 분리(의도된 순서):** W8(취약점 삽입 목록)은 담당 팀원이 보관 중이며, 답지 역할이라 모든 진단이 끝난 뒤 대조용으로 요청할 예정이다. 진단 중 넘겨받으면 독립 탐지의 의미가 사라지기 때문이다. 본 B4는 소스 직접 분석으로 담당 항목 근본 원인을 독립적으로 특정했고, "내가 찾은 것 vs W가 심은 것"의 W8 대조는 최종 커버리지 검증 단계로 둔다.
- **B5(재검증) 준비:** 위 근본 원인별로 조치판에서 확인할 지점 —
  - A10: `DEBUG=0`에서 디버그 페이지 미노출
  - A02: 기본 계정 제거·비밀번호 정책
  - A04: `PASSWORD_HASHERS` 교체(PBKDF2/argon2), `*_COOKIE_SECURE` 무조건 적용
  - A09: 실패 분기에 `security_log` + `_count_failure`/`_blocked` 실제 호출
- 조치판(W9 `secure`)이 올라오면 같은 스크립트로 재스캔·재현 비교.
