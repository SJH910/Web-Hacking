## 2. 상세

### A3-1. 약한 전화 인증번호 (A06)

- **대상 기능**: `/signup/phone/` 전화번호 인증 가입
- **원인**: 인증번호가 `random.randint(100, 999)`(3자리, 경우의 수 900)이고, 발송 안내문에 번호를 그대로 넣어 응답에 노출합니다. 시도 횟수 제한·만료도 없습니다.
  ```python
  sent = str(random.randint(100, 999))
  request.session['signup_code'] = sent
  message = f'{phone} 로 인증번호 {sent} 를 보냈습니다. ...'
  ```
- **재현 절차**:
  1. 전화번호만 전송 → 응답에 `인증번호 122 를 보냈습니다` 노출(실측).
  2. 그 번호로 재전송 → `가입이 완료되었습니다`.
  - 번호가 노출되지 않더라도 900회 내 전수 대입이 가능하고 막는 장치가 없습니다.
- **영향도**: High — 임의 전화번호로 계정 생성·가로채기.
  CVSS 3.1 ≈ 7.5 `AV:N/AC:L/PR:N/UI:N/S:U/C:L/I:H/A:N`
- **권고 조치**: 6자리 이상 + `secrets.randbelow()`로 생성, **응답에 번호 미포함**(실제 SMS 로만), 5분 만료 + 시도 5회 제한, 성공 시 세션값 폐기.
- **PoC**: `a0607.sh`

### A3-2. 로그인 시도 제한 없음 (A07)

- **대상 기능**: `/login/`, `/admin/login/` (둘 다 `limited_login` 래퍼)
- **원인**: `_blocked()`·`_count_failure()`를 정의만 하고 래퍼에서 **호출하지 않습니다**. 실패를 세지도, 잠그지도 않습니다.
  ```python
  def wrapped(request):
      ...
      response = login_view(request)
      if request.method == 'POST':
          if response.status_code == 200:   # 실패 — 그냥 통과
              pass
          else:
              security_log.info('login_ok ...')   # 성공 로깅만
      return response
  ```
- **재현 절차**: `admin`에 틀린 비밀번호 20회 연속 → 전부 `HTTP 200`(잠금·429 없음) → 직후 정답(`admin1234`) → `HTTP 302`(성공).
  ```
  시도 1..20 -> HTTP 200   (차단 메시지 없음)
  정답 로그인 -> HTTP 302   (제한 전혀 없음)
  ```
- **영향도**: High — 자격증명 전수 대입으로 계정(관리자 포함) 탈취.
  CVSS 3.1 ≈ 8.1 `AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:L/A:N`
- **권고 조치**: 이미 있는 `_count_failure`/`_blocked`를 실제로 연결 — `(IP, 아이디)` 쌍과 IP 전체 한도로 실패를 세고 한도 초과 시 차단. 또는 `django-axes` 도입. 공유 캐시·실제 클라이언트 IP(`X-Forwarded-For` 신뢰 설정) 전제.
- **PoC**: `a0607.sh`

### A3-3. 쿠키 `role=staff` 위조 — 권한 상승 (A08)

- **대상 기능**: `/attendance/board/` 직원용 현황판
- **원인**: 직원 여부를 서버 세션이 아니라 **클라이언트 쿠키**로 판정합니다.
  ```python
  if not (request.user.is_staff or request.COOKIES.get('role') == 'staff'):
      return redirect('/admin/login/?next=/attendance/board/')
  ```
- **재현 절차**: 일반 사용자(비직원)로 로그인 후
  - 쿠키 없이 `/attendance/board/` → `HTTP 302`(관리자 로그인으로 리다이렉트)
  - 쿠키 `role=staff` 추가 → `HTTP 200`(현황판 열림, 출결 수정 가능)
- **영향도**: High — 비직원이 전체 아동 출결 조회·수정(정산 근거 위조).
  CVSS 3.1 ≈ 8.1 `AV:N/AC:L/PR:L/UI:N/S:U/C:H/I:H/A:N`
- **권고 조치**: 권한은 서버 측(`request.user.is_staff` 또는 `profile.role`)으로만 판정. 쿠키 기반 검사 제거. 서명·암호화되지 않은 신뢰 쿠키를 권한에 쓰지 않음.
- **PoC**: `a08.sh`

### A3-4. 무검증 파일 업로드 (A08)

- **대상 기능**: `/my/` 서류 업로드(`doc`) → `Upload` 모델
- **원인**: `Upload`은 형식·크기 검사 없이 올린 파일을 원래 이름·확장자로 저장합니다(주석도 "위험한 파일도 막지 않는다").
- **재현 절차**: `.php` 웹셸을 가짜 MIME(`image/png`)로 업로드 → 거부 없이 `uploads/docs/webshell.php`로 저장 확인(컨테이너 디스크에서 확인).
- **영향도**: Medium(현재 구성) — 현재는 `urls.py`가 미디어를 서빙하지 않아 업로드 파일이 HTTP 로 직접 실행되지 않습니다. 다만 미디어를 서빙하거나 경로 노출 시 저장형 XSS/웹셸(RCE)로 즉시 상승합니다.
  CVSS 3.1 ≈ 6.5 `AV:N/AC:L/PR:L/UI:N/S:U/C:L/I:H/A:N` (서빙 구성에선 Critical)
- **권고 조치**: 공지 첨부(`NoticeFile`)처럼 매직바이트 판정 + 확장자 허용목록 + 크기 제한, 저장 이름 난수화, 웹루트 밖 저장, 실행 불가 응답(`Content-Disposition: attachment`, `X-Content-Type-Options: nosniff`). 참고: `NoticeFile`은 이미 올바르게 검증하므로 그 방식을 재사용.
- **PoC**: `a08.sh`
