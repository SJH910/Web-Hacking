# [W] 웹앱 구성과 팀 계획의 차이 — 설명 문서

- 담당: W
- 작성일: 2026-11-06
- 성격: 설명 문서. 태스크 완료 보고서가 아니다 (C4 보고서 통합 대상 아님)
- 상태: 팀 확인 필요. 아래 "팀에서 정해야 할 것" 참고

## 1. 요약

웹앱은 팀이 정한 스택(Django + SQLite)과 같다. 다만 **만든 순서와 저장소 구성이 `tasks.md`의 W 흐름과 반대**라서, 지금 상태로는 11/12 구현 완료와 11/10 블랙박스 진단 시작에 맞지 않는다.

- 팀 계획: 취약판(`vuln`)을 먼저 만들고 → 진단 → 조치판(`secure`)을 만든다
- 실제 진행: **방어를 넣은 앱을 먼저 만들었고**, 취약판은 그 앱에서 방어를 벗겨서 만들 예정이다. 취약판은 **아직 없다**

## 2. 팀 계획과 실제 구성

| 항목 | 팀 계획 (`tasks.md`) | 실제 구성 |
| --- | --- | --- |
| 만드는 순서 | 취약판 → 조치판 | 방어한 앱 → 취약판 (방어를 벗김) |
| 브랜치 | `vuln` / `secure` | 별도 저장소에서 `main`(방어) → `vuln/practice`(예정) |
| 저장소 | 이 저장소(`Web-Hacking`, 비공개) | 별도 비공개 저장소. 이 저장소에는 필요한 파일만 골라서 올린다 |
| 실행 환경 | 로컬 Docker Compose, `127.0.0.1` 바인딩 | **Docker 구성 없음.** 로컬 가상환경(venv)에서 실행 |
| 더미 데이터 시드 | W1 산출물 | **없음** (모의 데이터는 로컬 DB에만 있고 저장소에 없다) |
| OWASP 판 | `README.md`는 2025로 적었지만 `PLAN.md` 체크리스트는 **미결정** | 웹앱 쪽 내부 점검 문서는 2025판 번호를 쓰고 있다. C1에서 확정되면 이 표현도 맞춘다 |

## 3. W 태스크별 현황

"있음"은 해당 **기능이 있다**는 뜻이다. 취약점이 들어갔다는 뜻이 아니다.

| 태스크 | 요구 | 현황 |
| --- | --- | --- |
| W1 | 골격, Docker Compose, 시드 | 골격 있음 / Docker 없음 / 시드 없음 |
| W2 | 회원가입, 로그인, 비밀번호 재설정 | 로그인 있음 / 회원가입 없음 / 재설정 없음 |
| W3 | 게시글 CRUD, 검색, 댓글 | 목록·상세·검색 있음 / 글 작성·수정은 관리자 화면에서만 / 댓글 없음 |
| W4 | 파일 업로드·다운로드 | 없음 |
| W5 | 마이페이지, 관리자 페이지 | 둘 다 있음 |
| W6 | 외부 URL 미리보기 | 없음 |
| W7 | 설정, 의존성, 예외 처리 | 설정·의존성 목록 있음 / 취약 설정은 취약판에서 새로 만들어야 함 |
| W8 | 취약점 삽입 목록 | 취약판이 없어서 없음 (공개 시점은 `tasks.md` 규칙대로 3단계) |
| W9 | 조치판 | 방어한 앱이 이 역할에 가깝지만 만드는 순서가 반대 |

## 4. 일정 위험

- 현재 작업 순서(방어한 앱의 나머지 기능 → 취약판 분기)로는 **취약판이 11/12보다 늦어질 수 있다.** 작업량은 따져보지 않았고, 위험이 있다는 뜻이다
- 11/12 구현 점검(C3)에서 미완성 항목이 나오면 `PLAN.md`의 규칙(범위에서 빼거나 Juice Shop 등으로 대체)을 적용해야 한다

## 5. S2가 `docs/B1.md`에서 요청한 정보

| 요청 | 답 |
| --- | --- |
| 로그인 방식 | Django 기본 세션 쿠키(`sessionid`). 관리자·직원은 `/admin/login/`, 일반 사용자는 `/login/` |
| 스캔 제외 경로 | W8 공개와 **분리해서 취약판 배포와 동시에** 전달한다 (능동 스캔이 W8 공개보다 먼저 시작하므로). 경로만 알리고 취약점 위치는 포함하지 않는다. 지금 확정된 것은 로그아웃 `POST /admin/logout/` 뿐이며, 데이터를 삭제하는 관리자 화면 경로도 목록에 넣는다 |
| `requirements.txt` | 있다 (`Django`, `asgiref`, `sqlparse`). 취약판에서는 구버전 항목을 별도로 둘 예정이라, 진단 대상은 취약판의 파일이 올라온 뒤 확정된다 |

## 6. 팀에서 정해야 할 것

- [ ] **진단 대상 범위**: 11/12 시점에 있는 기능만 대상으로 하는가, 아니면 취약판 완성을 기다리는가
- [ ] **취약판 전달 방식**: 이 저장소 `vuln` 브랜치에 파일을 올리는가, 별도 저장소를 공유하는가 (이름 규칙은 팀 규칙을 따를 수 있다)
- [ ] **Docker 구성**: ZAP이 컨테이너에서 돌기 때문에 호스트 `127.0.0.1`에서만 도는 앱은 접근하지 못할 수 있다. 웹 서비스 하나를 compose에 넣고 포트는 `127.0.0.1`에만 열며 ZAP은 compose 내부망으로 접근하는 구성을 제안받았다 (DB가 SQLite라 DB 컨테이너는 불필요). 이 구성으로 W1에서 만든다 — 팀 확인 후 확정

## 7. 변하지 않는 것

- 공격은 `127.0.0.1` 로컬에서만 한다
- 더미 데이터만 쓴다. 실제 아동·보호자 정보는 쓰지 않는다
- 취약판은 인터넷에 올리지 않는다
