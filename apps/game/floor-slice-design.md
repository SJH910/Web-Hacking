# 첫 관문 설계 — 수직 슬라이스 (게임 기획)

- 담당: 게임 기획
- 목적: 한 층을 처음부터 끝까지 플레이할 수 있는 MVP의 **규칙·데이터 계약**을 확정한다.
- 전제: 브라우저 게임, 배포 플랫폼 미정(Vercel 미배포). 모든 데이터는 **가상·합성**이며 실제 요청·공격은 없다.
- 관련 문서: [plan.md](./plan.md) · [team-roles.md](./team-roles.md) · [project-structure.md](./project-structure.md)

> 현재 프런트 목업(`app/page.tsx`)은 화면 셸(시나리오 선택·조사·결과·동료)만 있고 **퍼즐 판정·완료 조건이 없다.** 이 문서가 그 빠진 규칙을 채운다.

---

## 1. 목표·스토리

- **관문명:** 기록의 문 (수직 슬라이스용 1관문)
- **한 줄 목표:** 흩어진 **기록(증거)** 을 읽고, 동료 '라온'의 흐릿한 기억에 휘둘리지 않고 **무엇이 문제인지 스스로 판정**한다.
- **학습 메시지:** "AI 동료의 말을 그대로 믿지 말고 **증거로 검증**한다." (plan.md 핵심)

## 2. 플레이 흐름 (상태 전이)

```
시나리오 선택 → 행동 선택(관찰/상호작용) → 조사 실행
   → 증거 공개(findings) → [판정 단계] → 정답/오답
   → (정답 누적) 봉인 해제 → 관문 통과
```

- 현재 목업에 **없는 핵심 추가 = [판정 단계]**: 증거를 본 뒤 플레이어가 결론을 고르는 단계. 이게 "게임"의 알맹이다.
- `관찰`과 `상호작용`의 차이(현재 동일): **관찰**은 증거만 열람, **상호작용**은 라온에게 질문해 힌트를 얻을 수 있음(단, 라온은 가끔 틀림 → §6).

## 3. 허용 행동 (화이트리스트)

| 행동 | 설명 | 부작용 |
|---|---|---|
| 시나리오 선택 | 3개 중 1개 | 없음 |
| 조사 실행 | 해당 시나리오의 증거 공개 | 없음(합성 데이터 조회) |
| 라온에게 질문 | 준비된 힌트 반환 | 신뢰도 변동(§6) |
| 결론 판정 제출 | 보기 중 선택 | 점수·봉인 변동 |

- 그 외 자유 입력·명령·실제 요청은 **없음**(게임은 시뮬레이션 전용).

## 4. 조작 모델 — 탐색(가상 터미널/웹뷰) + 결정적 판정

객관식만으로는 쉽고 단조롭다. 핵심 재미는 **플레이어가 직접 조사·시도하는 탐색**에 둔다.

### (1) 탐색 — 가상 터미널 / 가상 웹뷰 (메인)

- 허용된 **명령·입력**으로 플레이어가 증거를 직접 캔다. 각 명령·입력은 서버가 **미리 짜 둔 합성 출력**을 반환한다(실제 실행·네트워크 요청 없음).
- 예(로그 분석): `cat access.log` · `grep "login fail"` · `count ip` · `diff 시도 vs 기록`
- 예(인젝션류): 가상 검색창에 `' OR '1'='1` 입력 → **시뮬 유출 결과** 노출
- 화이트리스트 밖 명령/입력은 **"허용되지 않음"** 으로 안전 차단(임의 셸·명령 없음).

### (2) 판정 — 결정적 (마무리, 축소)

완료 조건 두 축:
- **행동 기반:** 핵심 명령/페이로드를 실제로 찾아 실행했는가(예: 올바른 주입 입력으로 시뮬 유출 트리거).
- **결론 기반:** 분류 → 취약/정상/증거부족(`needs_review`) → 조치 (객관식 또는 핵심어 입력).
- 객관식은 **마무리 확인용**으로만, 메인은 탐색이다.

### 규칙

- **정답·터미널 출력·완료 규칙은 전부 결정적이며 서버 보관**(X1=백엔드 판정). 클라이언트엔 정답이 없어 랭킹 조작을 막는다.
- LLM 자유 응답에 판정을 맡기지 않는다(제약).
- 탐색만으로(동료 힌트 없이) 풀 수 있어야 한다.

## 5. 시나리오 데이터 (증거·정답·힌트)

수직 슬라이스는 **시나리오 1개(기록 보관소)를 완전 구현**하고, 나머지 2개는 같은 틀로 확장한다.

### 5-1. 기록 보관소 (로그 분석 · 쉬움) — 완전 명세

- **증거(findings):**
  | # | 제목 | 상세 |
  |---|---|---|
  | 01 | 반복된 접근 시도 | 같은 세션에서 짧은 시간에 로그인 요청이 연속 기록됨 |
  | 02 | 실패 뒤 성공 | 다수 실패 응답 후 1건 성공 응답이 이어짐 |
  | 03 | 기록되지 않은 실패 | 실패 시도 일부가 로그에 남지 않음 |

- **판정 정답:**
  1. 분류 → **인증 시도 남용(무차별 대입) + 실패 미기록** `[정답: 무차별 대입 흔적]`
  2. 판정 → **취약** (반복 실패+미기록은 탐지·차단 부재)
  3. 조치 → **시도 횟수 제한·잠금 + 실패 로그 기록**

- **힌트 단계(라온 질문 시):**
  - 1단계(기본): "접근 기록이 유난히 촘촘해. 횟수를 세어볼까?"
  - 2단계(자세히): "실패가 많은데, 그 실패가 **전부** 기록됐는지 비교해봐."
  - 3단계(거의 정답): "막는 장치도, 남기는 장치도 없어 보여 — 그게 핵심이야."

### 5-2. 유리문 로그인 (권한 검토 · 보통) — 틀만

- 핵심: 로그인 흐름에서 **권한 값이 요청 측에서 정해짐**(접근 통제 결함). 정답 판정: 취약 / 조치: 권한은 서버 세션으로만 판정.

### 5-3. 제어실 온실 (응답 검토 · 보통) — 틀만

- 핵심: **응답 헤더에 과도한 정보 노출**(버전·내부 경로). 정답 판정: 취약(낮음) / 조치: 불필요 헤더 제거.

> 2·3번의 증거·보기·힌트 세부는 1번과 동일 포맷으로 추후 확정(팀 결정 §10).

## 6. 동료 '라온'의 불완전성 규칙

- 라온은 **각 시나리오에서 1회, 의도적으로 틀린 첫마디**를 던진다(예: "그냥 로그가 좀 많은 거 아냐?").
- 플레이어가 **라온의 틀린 말대로 판정하면 오답**이 되도록 보기를 구성한다(함정 보기 = 라온의 주장).
- 신뢰도(기본 64%): **증거로 바로 정답 → +**, **오답·라온 의존 → −**. (구체 수치는 §7)
- LLM 담당은 라온 대사를 **스키마(확신도·근거 지정)** 로 반환하고, 판정 권한은 갖지 않는다(team-roles 합의).

## 7. 완료·실패 조건 / 점수·신뢰도

- **관문 통과:** 3단 판정을 모두 정답 → 봉인 해제(진행도 꽉 참) → 다음 층.
- **실패 없음(재시도형):** 오답은 점수·신뢰도만 깎고 재시도 허용(학습 도구 성격).
- **점수(제안):** 단계 정답 +20, 오답 −5(0 하한). 힌트 1단계 사용 시 해당 단계 가점 −5.
- **신뢰도(제안):** 무오답·무힌트 정답 시 +2, 오답 시 −3(0~100).
- (수치는 밸런스용 초안 — §10 결정 대상)

## 8. 데이터·상태 계약 (구현 담당자용)

프런트·백엔드가 공유할 **시나리오/판정 데이터 형식**(초안). 구현 전 합의 필요.

```ts
type Choice = { id: string; label: string; correct: boolean; isTrap?: boolean };
type PuzzleStep = {
  key: "classify" | "verdict" | "action";
  question: string;
  choices: Choice[];      // 정답 correct:true 정확히 1개
  why: string;            // 정답 해설(증거 근거)
};
type Evidence = { number: string; title: string; detail: string; tag: string };
type Hint = { level: 1 | 2 | 3; text: string };

// 탐색: 허용 명령/입력 → 합성 출력 (서버 보관)
type Command = {
  key: string;            // 완료 조건에서 참조할 식별자
  pattern: string;        // 허용 명령/입력(정규식). 예: "^grep .*fail"
  output: string;         // 서버가 반환할 합성 출력
  reveals?: string[];     // 이 명령이 드러내는 Evidence number
};
type Completion = {
  requiredActions?: string[]; // 반드시 실행해야 할 Command.key (행동 기반)
  steps: PuzzleStep[];        // 마무리 판정 (결론 기반)
};

type Scenario = {
  id: string; title: string; category: string; difficulty: string;
  surface: "terminal" | "webview";  // 탐색 표면
  evidence: Evidence[];
  commands: Command[];     // 탐색 화이트리스트 (서버)
  completion: Completion;  // 행동 + 결론 완료 조건
  hints: Hint[];           // 라온 질문 시 단계별
  allyOpening: string;     // 라온의 (의도적으로 틀린) 첫마디
  flag: string;            // 통과 보상 문자열
};
type FloorState = {
  floor: number;           // 1부터
  scenarioId: string;
  ranAll: string[];        // 실행한 Command.key
  progress: number;        // 완료한 step 수 0..3
  score: number;
  trust: number;           // 라온 신뢰도 0..100
  cleared: boolean;
};
```

- **판정은 전부 서버에서** 결정적으로 수행(X1=백엔드). 터미널 입력·판정 제출을 서버가 받아 `output`/정오/점수를 돌려준다. `commands`·`completion`·정답은 **클라이언트에 내려보내지 않는다**(랭킹 조작 방지).
- 프런트는 **가상 터미널/웹뷰 탐색 UI** + §2의 **[판정 단계] UI**(보기 선택·정오·해설)를 구현한다(현재 없음).
- **세이브/랭킹:** 개인 진행은 `localStorage`(FloorState), 랭킹은 서버가 점수·진행도를 저장·집계.
- **vulnscan 연동(선택):** `Evidence`·`output`을 vulnscan 소견 JSON(`owasp/title/evidence`)에서 **구워서** 채울 수 있다(실시간 요청 아님). 매핑표는 별도 합의.

## 9. 예외 흐름 점검 (기획 관점)

| 흐름 | 기대 동작 |
|---|---|
| 조사 전에 판정 시도 | 판정 단계 비활성(증거 먼저) |
| 오답 반복 | 재시도 허용, 점수 하한 0 |
| 힌트 남용 | 가점만 감소, 정답은 여전히 가능 |
| 라온 말대로 판정 | 함정 보기 → 오답 처리 + "증거 재확인" 유도 |
| 시나리오 변경 | 진행도·결과 초기화 |

## 10. 결정 현황

**결정됨**
- **층 번호:** 프런트 "제3층" 표기 → **1층부터 순차 진행**으로 통일.
- **진행 방식:** **세이브/이어하기 + 진행도 랭킹** 추가. 세이브(개인)=`localStorage`, 랭킹(공유)=백엔드 저장.
- **판정 주체(권고):** MVP 수직 슬라이스는 **프런트 판정**, **랭킹 단계에서 백엔드 판정+저장으로 이전**(팀장 확정 대기).

**남은 확정 (게임 기획 후속)**
- **점수·신뢰도 수치**(§7 초안) — G4.
- **2·3번 시나리오** 증거·보기·힌트 세부 — G6.
- **판정 단계 UI 위치**(결과 패널 내부 vs 별도 단계) — 프런트와 합의 — F1.
- **vulnscan 연동 여부**(§8) — 하면 백엔드·보안과 매핑 합의 — B5.
