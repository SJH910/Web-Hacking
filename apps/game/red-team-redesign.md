# 용범의 탑 — 레드팀 전면 재설계 (기획안)

- 담당: 게임 기획 (황선정)
- 상위: [tasks.md](./tasks.md) · [problem-pool.md](./problem-pool.md)(X3) · [scoring-trust.md](./scoring-trust.md)(G4) · [ending-branches.md](./ending-branches.md)(G7)
- 상태: **합의용 초안.** 확정 시 기존 풀(19문제·3단 판정)을 폐기하고 본 모델로 교체.

> **전환 이유:** 기존 19문제는 "로그·헤더를 **분석하고 취약/양호를 판정**"하는 **블루팀** 방식이다. 실제 웹 해킹(레드팀)은 **취약한 웹앱을 탐색해 단서를 찾고 직접 공격해 침투**한다. 문제를 전부 **레드팀**으로 다시 만든다.
>
> **핵심:** 문제마다 **가상 취약 웹페이지**를 두고, 플레이어가 그 안을 **탐색 → 단서 발견 → 익스플로잇 → FLAG 캡처**한다. 캡처 후 **한 줄 마무리**(무슨 취약점이었나)로 학습을 남긴다.

---

## 1. 결정 요약 (이번 합의)

| 항목 | 결정 |
|---|---|
| 승리 조건 | **FLAG 캡처 + 짧은 마무리** — 익스플로잇으로 `FLAG{…}` 획득·제출 → 통과, 끝에 취약점 한 줄 |
| 프레임워크 | **탑 구조 유지**(10층·세이브·랭킹·라온·엔딩), **점수·신뢰도는 익스플로잇 기반으로 재설계** |
| 상호작용 | **혼합** — 1~3층 가이드형, 4~8층 혼합, 9~10층 실제 요청 편집(Burp식) |

## 2. 핵심 모델 — 한 층 = 가상 취약 웹앱

각 층은 **합성 취약 미니 웹앱**(테마가 있는 가짜 사이트)이다. 플레이어 흐름:

```
① 라온 첫마디(가끔 틀린 유도)
② 탐색   — 페이지 열람·링크 클릭·소스 보기(HTML 주석)·robots.txt·에러 유발·쿠키 확인
③ 단서   — 페이지/응답에 심긴 힌트 발견(숨은 링크·순차 ID·스택트레이스·설정 노출…)
④ 익스플로잇 — 티어별(폼 조작 / 필드 편집 / 요청 편집)로 공격 수행
⑤ FLAG   — 서버가 공격 성공 조건 충족을 확인하면 FLAG{…} 노출
⑥ 제출·통과 — FLAG 제출로 클리어 → "무슨 취약점이었나" 한 줄 마무리
```

### 시뮬레이션·결정성 보장 (불변식 유지)
- **실제 네트워크·실행 없음.** 미니 웹앱 페이지와 모든 응답은 **서버 고정 합성 스크립트**. SSRF·XSS도 **진짜 요청/실행 안 함** — 페이로드 **class를 결정적으로 매칭**해 합성 결과를 돌려준다.
- **FLAG는 서버 보관**, 공격 성공 조건을 서버가 검증했을 때만 노출(클라이언트에 미리 안 보냄).
- 모든 데이터·비밀·세션은 가짜.

## 3. 상호작용 티어 (난이도 연동)

| 티어 | 층 | 방식 | 단서 난이도 |
|---|---|---|---|
| **guided** | 1~3 (쉬움) | 페이지 UI 클릭·폼 제출, **지정 필드 1곳 편집**/페이로드 **선택** | 눈에 띔(HTML 주석·보이는 숨은 링크) |
| **mixed** | 4~8 (보통) | 일부 **요청 편집**(파라미터·쿠키 변경) + 응답 읽기 | 한두 단계 탐색 |
| **raw** | 9~10 (어려움) | **실제 요청 편집**(URL·헤더·쿠키·바디·토큰), 원시 응답, 다단계 체인 | 숨어 있음·조합 필요 |

> 초보도 1~3층을 "클릭·선택"으로 넘고, 후반엔 진짜 요청을 손으로 조작하게 해 **실전 전이**를 만든다.

## 4. 점수·신뢰도 재설계 (G4 교체)

판정(분류→판정→조치)이 사라지므로 점수 축을 **공격 수행**으로 바꾼다.

### 층 점수
```
floorScore = exploitBase[난이도]        // 쉬움 10 / 보통 15 / 어려움 20
           + clueBonus * 발견단서수      // 단서 발견 +3/개
           - wrongAttempt * 틀린시도      // 헛발 -3
           - hintPenalty * 사용힌트       // 힌트 -3
           + cleanBonus(힌트0·오답0)      // +5
```

### 신뢰도 (라온 관계 — 레드팀 재해석)
- 시작 60.
- **라온의 틀린 유도를 따라 헛발** → −5 (함정). **라온 무시하고 독자 성공** → +3.
- 힌트 사용 → −1. 층 클린 클리어 → +2. 종료 시 ≥80이면 보너스 +20.
- 라온은 **공격 힌트**를 주되 **가끔 엉뚱한 파라미터·방향으로 오도**한다(판정은 안 함).

### 엔딩 (G7 유지, 축 재해석)
- 기존 6엔딩 서사 **그대로 재활용 가능** — 축이 "라온과의 관계"라 레드팀에서도 유효.
- 정확도 축 = **익스플로잇 효율**(precise=적은 헛발·독립적 / struggle=많은 헛발·라온 의존).
- 신뢰도 축 = 동일. → `(신뢰도 상/중/하) × (정확도 precise/struggle)` 매핑 유지.

## 5. 라온 (L) — 변경 최소

- 여전히 **판정 안 함.** 이제 **공격 힌트**(어디를 찌를까)와 **의도적 오도**를 준다.
- LLM 교체 구조([[raon-llm-setup]]) 그대로 — `allyOpening`·힌트를 Ollama/자체모델로 윤문, 실패 시 고정 대사.
- 데이터 경계 유지: 라온에 **FLAG·정답 익스플로잇 미전송**, 층·발견 단서·신뢰도만.

## 6. 챌린지 스키마 (풀 교체)

```ts
type Tier = "guided" | "mixed" | "raw";

type Challenge = {
  id: string; title: string;              // 방 이름(테마)
  difficulty: "쉬움" | "보통" | "어려움";
  owasp: string; tier: Tier;
  site: {
    entry: string;                        // 시작 경로 "/"
    pages: Page[];                        // 합성 페이지(HTML·폼·링크·주석)
    rules: ActionRule[];                  // 플레이어 행동 → 합성 응답(결정적, 위에서 첫 일치)
  };
  clues: Clue[];                          // 페이지/응답에 심긴 단서(발견 시 점수·진행)
  exploit: { condition: string; flag: string };  // 성공 조건(서버 검증) → FLAG
  allyOpening: string; hints: Hint[];     // 라온(판정 안 함)
  wrapUp: string;                         // 캡처 후 한 줄: 무슨 취약점·왜
};

type ActionRule = {               // 클릭·폼 제출·편집 요청 모두 하나의 모델로
  when: string;                   // 요청 매칭(method·path·query·cookie·header·body·payload class)
  status: number; headers?: KV[]; body?: string;
  reveals?: string[];             // 공개되는 단서 id
  grantsFlag?: boolean;           // 이 응답이 exploit 성공이면 FLAG 노출
};
```

- `clues`는 "발견형"(소스 보기·robots·에러 등 탐색으로 드러남). 발견이 공격의 **힌트**가 된다.
- `exploit.condition` 충족 전까지 FLAG 미노출. 판정 단계(steps) 없음 — **성공=캡처**.

## 7. 예시 챌린지 (대표 4개 — 모델 검증용)

### C1. 열린 로비 — A01 접근통제(IDOR) · guided · 쉬움
```
사이트: 쪽지함. visitor로 로그인된 상태.
 entry /inbox → 내 쪽지 목록, 각 링크 /note?id=18
 소스 주석: <!-- note ids are sequential -->   (단서 clue-seq)
탐색: 내 쪽지는 id=18. 주석에서 "순차 ID" 발견.
익스플로잇(guided): id 필드를 18→19로 바꿔 열기
 rules: /note?id=18 → 200 내 쪽지
        /note?id=19 → 200 "관리자 쪽지: 임시비번 리셋 링크 … FLAG{idor_sequential_notes}"  grantsFlag
 exploit.condition: 내 소유 아닌 id 200 열람
라온(틀림): "네 쪽지함만 보면 돼. 다른 번호는 막혀 있을 거야."
wrapUp: "번호만 바꿔 남의 자원 접근 — IDOR(접근 통제). 서버가 소유권을 확인해야."
```

### C2. 거울 게시판 — A05/A03 반사형 XSS · mixed · 보통
```
사이트: 방명록. 검색 ?q= 가 입력을 그대로 표시.
 소스: 검색 결과 영역이 입력을 이스케이프 없이 출력(단서 clue-noescape). CSP 없음.
익스플로잇(mixed): q에 실행형 페이로드 주입
 rules: q=안녕          → 200 정상 반사
        q=<script>…</script>(실행형 class) → 200 "관리자가 링크 클릭함 · 세션=FLAG{reflected_xss_admin_cookie}" grantsFlag
 exploit.condition: q에 실행형 스크립트 페이로드 반사(실제 실행 없음·class 매칭)
라온(틀림): "그냥 글자가 보이는 거야, 위험할 거 없어."
wrapUp: "입력이 이스케이프 없이 반사 — 반사형 XSS. 출력 인코딩·CSP 필요."
```

### C3. 참·거짓의 문 — A03 SQLi(로그인 우회) · mixed · 보통
```
사이트: 로그인 폼 (user/pw).
 에러: pw에 ' 입력 시 SQL 오류 문자열 노출(단서 clue-sqlerror).
익스플로잇(mixed): user 또는 pw에 ' OR '1'='1 -- 주입
 rules: 정상 자격       → 200 실패/성공 일반
        user=' OR '1'='1 -- → 200 "admin으로 로그인됨 · FLAG{auth_bypass_sqli}"  grantsFlag
 exploit.condition: 인증 우회 페이로드로 admin 세션
라온(틀림): "비번을 모르면 못 들어가, 추측은 시간 낭비야."
wrapUp: "입력이 쿼리 논리로 해석 — SQLi 인증 우회. 파라미터 바인딩."
```

### C4. 두 얼굴의 문지기 — A08/A02 JWT alg=none 권한상승 · raw · 어려움
```
사이트: 대시보드. 요청에 Authorization: Bearer <jwt {alg:none, role:user}>.
 탐색(raw): 요청 편집으로 토큰 확인 → base64 디코드 {alg:none,role:user}.
           /admin 404/403 응답 헤더에 verify=off 단서(clue-nosig).
익스플로잇(raw): payload role=admin 으로 재인코드 후 /admin 요청
 rules: 원본 토큰 /admin         → 403
        alg=none·role=admin /admin → 200 "관리 콘솔 · FLAG{jwt_alg_none_privesc}"  grantsFlag
 exploit.condition: 미서명 토큰 위조로 /admin 200
라온(틀림): "토큰은 서버가 발급한 거라 못 바꿔."
wrapUp: "서명 미검증 토큰 위조 — 무결성 실패. alg 고정·서명 검증 강제."
```

## 9. 담당 인계 · 기존 작업 영향

| 역할 | 할 일 | 영향 |
|---|---|---|
| 기획(G) | 챌린지 저작(사이트·단서·익스플로잇·라온·마무리), 본 모델·풀 확정 | X3·pool-problems **교체** |
| 백엔드(B) | **엔진 교체** — 미니 웹앱 서빙 + 행동→응답 규칙 + 익스플로잇 조건 검증 + FLAG 발급. 게임 코어 네트워크 금지 유지(합성) | #16의 **3단 판정·terminal/choice 엔진 상당 재구성** |
| 프런트(F) | **브라우저형 탐색 UI**(페이지 렌더·소스 보기·폼·요청 편집기·FLAG 제출). 티어별 모드 | play 화면 **재구성** |
| LLM(L) | 공격 힌트·오도 대사(판정 안 함). [[raon-llm-setup]]·#20 계약 재활용 | 라온 역할 소폭 변경 |

> **영향 큼:** #16 백엔드 엔진과 FE 플레이 화면을 **상당 부분 다시** 만든다. 팀장(본인) 결정 사안이며, B·F와 합의 필요. 마이그레이션은 **점진 전환 권장**(기존 유지한 채 레드팀 모드 신설 → 챌린지 쌓이면 전환) 또는 **전면 교체** 중 택1.

## 10. 미정 · 논의

- **마이그레이션:** 점진(신 모드 병행) vs 전면 교체 — B·F 부담과 일정에 따라.
- **FLAG 제출 방식:** 입력창 제출 vs 자동 감지(공격 성공 시 자동 통과).
- **요청 편집 자유도(raw):** 완전 자유 텍스트 vs 핵심 필드만(판정 단순화).
- **단서 탐색 도구:** 소스 보기·robots·쿠키 뷰어·요청 히스토리 중 어디까지 FE에 둘지.
- **저장형 XSS 등 다단계**를 결정적으로 모델링하는 범위.
